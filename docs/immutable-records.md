# Immutable messaging and audit architecture

## Why an Express route wrapper was selected

A Mongoose `post('save')` hook knows that a document changed, but it does not naturally know the business meaning of the HTTP action. For example, the same custody document save could mean `custody.updated` or `custody.swap_accepted`. Passing action names into model hooks would couple the persistence layer to request-specific behavior.

The `auditedRoute` Express wrapper keeps semantic action names at the route boundary while centralizing all audit mechanics. Controllers perform business validation and persistence only; they contain no `AuditLog.create()` calls.

For each audited request, the wrapper:

1. Starts a MongoDB transaction and exposes its session to the controller.
2. Loads and snapshots the target document before mutation when applicable.
3. Temporarily captures the controller's JSON response instead of sending it.
4. Extracts the resulting entity state from that response.
5. Inserts one `AuditLog` containing the actor, semantic action, entity, previous state, new state, and server timestamp.
6. Commits the business mutation and audit insert together.
7. Sends the captured response only after the commit succeeds.

If validation or audit insertion fails, MongoDB rolls back both writes and the client never receives a success response. The design therefore avoids the dangerous state where an action succeeds but its audit entry is missing.

## Immutability layers

- Message and audit routers expose only creation/read operations; no PATCH, PUT, or DELETE endpoints exist.
- Mongoose middleware rejects document saves after creation, query updates, replacements, deletions, and bulk-write mutations for both models.
- `MessageLog.editedFlag` is immutable and validates that its value is always `false`.
- Timestamps are generated by the server and marked immutable.
- Family-membership authorization protects both message and audit reads.

Omitting mutation routes is stronger than hiding buttons because a caller using Postman, curl, or a custom client still has no application endpoint capable of changing the record.

## Honest security boundary

This implementation provides append-only guarantees at the Express and Mongoose application layers. A database administrator with direct Atlas write access can still modify MongoDB collections, so the records should not be described as cryptographically tamper-proof or court-certified evidence. A production legal-evidence system would additionally use restricted database roles, off-site write-once retention, cryptographic hash chaining, signed timestamps, and independent backups.

## Pagination and ordering

Messages and audit entries use opaque cursors containing both timestamp and ObjectId, preventing duplicates or skipped records when multiple actions share the same millisecond. Messages are returned chronologically for natural chat rendering, while audit pages are sorted newest first for the timeline.
